# v.2.3.0
Versión menor: añade la API nueva de validación y marca como obsoleta la antigua, que sigue funcionando igual. La 3.0.0 sólo quitará lo obsoleto.

API nueva (Kitpymes.Core.Validations y Kitpymes.Core.Validations.Abstractions):
- IValidator<T>.ValidateAsync devuelve un Result de Kitpymes.Core.Results: correcto, o un Error de validación (código Validations.Invalido) con un FieldError por cada campo que falla. No lanza excepciones por datos inválidos.
- Validator<T>: base para escribir validadores con RuleFor y RuleForEach. Reglas: Required, MaxLength, MinLength, Email, Name, Subdomain, Matches, GreaterThan, GreaterThanOrEqual, LessThan, LessThanOrEqual, Between, Equal, NotEqual, IsInEnum, Must (también con el objeto entero, para reglas entre campos) y Custom (varios errores en un campo). Modificadores: When, WithName, WithMessage, WithErrorCode, ContinueOnError. SetValidator para objetos anidados e Include para reglas comunes.
- El campo de cada error lleva la ruta de un formulario de Angular: camelCase como System.Text.Json (respeta [JsonPropertyName]), con puntos y con el índice en las colecciones (address.street, lines.0.name).
- Por defecto se para en el primer error de cada campo. Un ciclo entre objetos no se valida dos veces y a más de 32 niveles se da Validations.Profundidad.
- Los códigos están en ValidationErrorCodes (Validations.Requerido, Validations.LongitudMaxima...). Los propios, con WithErrorCode o en Custom, tienen la forma Modulo.Motivo y no pueden usar el prefijo Validations.
- Mensajes en español por defecto e inglés con la cultura en, elegidos al validar.
- Un validador no guarda estado entre validaciones: se registra como singleton y se puede usar desde varios hilos a la vez.

Paso del mediador (Kitpymes.Core.Mediator):
- services.LoadValidations(o => o.WithAssemblies(...)) registra los validadores de los ensamblados, un paso general (IPipelineBehavior) que valida cada comando y consulta antes del manejador y devuelve el fallo sin llamarlo, y la comprobación de arranque (IValidationStartupCheck).
- La comprobación de arranque falla si un comando o consulta con algún dato de entrada (propiedad pública legible o campo público) no tiene validador, si tiene más de uno, si el paso no está registrado o si un validador está mal configurado (una regla sobre el objeto entero sin WithName).

FluentValidation (Kitpymes.Core.Validations.FluentValidation), como adaptador de ejemplo:
- FluentValidationAdapter<T> expone un validador de FluentValidation como IValidator<T>, con las mismas rutas (Items[0].Name pasa a items.0.name) y los mismos códigos (NotEmpty da Validations.Requerido; un código propio válido se respeta).
- services.LoadFluentValidationAdapters(...) registra los validadores de FluentValidation y sus adaptadores. Hay que llamar también a LoadValidations(o => o.WithAssemblies(...)) para el paso y la comprobación de arranque.

Obsoleto (se elimina en la 3.0.0; cada aviso dice qué usar):
- KPY0005: Validator (estático), ValidatorRule y ValidatorRuleOptions.
- KPY0006: ValidationsException.
- KPY0007: ValidationsMiddleware, LoadValidations(IApplicationBuilder), ValidationsSettings, LoadValidations() y LoadValidations(ValidationsSettings), ValidationsOptions.WithEnabled y ValidationsOptions.ValidationsSettings.
- KPY0008: las extensiones de reglas de FluentValidation (IsEmail, IsName...), LoadFluentValidation, FluentValidationSettings y ValidationResultExtensions.

Cambios de comportamiento:
- LoadValidations(Action<ValidationsOptions>) sigue aceptando unas opciones nulas, como en la 2.2.0, y no configura nada.
- En la API nueva, GreaterThan, LessThan y Between comparan los textos por ordinal, sin cultura: "B" va antes que "a".
- Ninguno en la API antigua: lo obsoleto funciona igual que en la 2.2.0.

Dependencias (la validación de paquete no las ve):
- Kitpymes.Core.Results pasa de 1.0.1 a 1.2.1, también en Abstractions. Lo que cambia para quien la usa de rebote (ver sus notas):
  - ApiResult.Error(...) sin mensajes y WithErrors(tuplas) con un campo o mensaje vacío lanzan ArgumentException en lugar de SharedException (1.2.0): un catch (SharedException) deja de capturarlo.
  - WithErrors(tuplas) con un campo repetido suma sus mensajes en lugar de quedarse con el último (1.2.1).
  - Trae el analizador KPY0003 (1.1.0): un Result que se descarta sin mirarlo da error de compilación; '_ =' es el descarte explícito.
  - Los tipos Result y Error (1.1.0) pueden chocar (CS0104) con otra librería que tenga los mismos nombres; se resuelve con un alias de using.
  - Quien referencie Kitpymes.Core.Results 1.0.1 de forma explícita recibe NU1605 (bajada de versión): hay que subirla a 1.2.1.
- Kitpymes.Core.Mediator.Abstractions 1.0.1 es nueva y llega también a quien sólo usa la API antigua.
- IValidator<T> se llama igual que el de FluentValidation: en un fichero con los dos using, use un alias.

Los avisos de obsoleto rompen la compilación con TreatWarningsAsErrors. Mientras se migra, se pueden silenciar con <NoWarn>$(NoWarn);KPY0005;KPY0006;KPY0007;KPY0008</NoWarn>.

La validación de paquete compara con la 2.2.0.

# v.2.2.0
Versión menor y no parche: corrige un fallo grave, pero cambia el comportamiento de quien encadenaba reglas de una forma que ya no se admite (abajo).

Fallo corregido: todas las reglas de todas las peticiones iban a una misma lista estática.
- Con dos validaciones a la vez (dos peticiones web, dos hilos), una podía recibir los errores de la otra, y el Throw() de una lanzaba o borraba los errores de la otra: una petición con datos inválidos podía pasar la validación. En paralelo también podían saltar excepciones como NullReferenceException o IndexOutOfRangeException, porque la lista no era segura entre hilos.
- Una regla que fallaba sin que nadie llamara a Throw() (por una excepción o un return en medio) dejaba su error en la lista para la siguiente validación, fuera de quien fuera.
- Ahora cada cadena que empieza en Validator.AddRule tiene sus propios errores, y AddRule sobre una cadena añade a esa misma cadena.

También corregido:
- StopFirstError() en medio de una cadena se perdía (cada AddRule devolvía una cadena nueva); ahora vale para toda la cadena.
- StopFirstError() decía parar en el primer error, pero seguía evaluando todas las reglas y sólo recortaba el mensaje. Ahora, con un error ya guardado, las reglas que se añaden después no se evalúan (una regla que daba por hecho que la anterior había pasado ya no lanza).
- ThrowAsync ya no usa Task.Run: se ejecuta en el mismo hilo y el error sigue llegando en la tarea devuelta.

Cambios de comportamiento:
- Los errores ya no pasan de una cadena a otra. Si alguien hacía Validator.AddRule(a, ...); y luego Validator.AddRule(b, ...).Throw(); esperando que saliera también el error de a, ahora sólo sale el de b. Hay que encadenar: Validator.AddRule(a, ...).AddRule(b, ...).Throw();
- Las reglas de ValidatorRuleOptions (IsEmail, IsNullOrEmpty...) escriben en su propia cadena, también desde otro hilo o después de un await dentro de las opciones. Pero un ValidatorRuleOptions creado a mano (new ValidatorRuleOptions(valor).IsEmail()) no tiene cadena y lanza InvalidOperationException; antes añadía el error a la lista estática.
- ValidatorRule.Add (público, para reglas propias) sólo se puede usar dentro de las opciones de una regla, en el mismo hilo y antes de que terminen. Fuera lanza InvalidOperationException; si es después de un await dentro de unas opciones async, esa excepción no llega a quien llamó y tumba el proceso, como cualquier excepción en un método async void.
- Con StopFirstError() antes en la cadena, las reglas posteriores al primer error no se evalúan (ver arriba).

Sin cambios en la API pública. La validación de paquete compara con la 2.1.0.

# v.2.1.0
Versión menor y no parche: corrige vulnerabilidades sin cambiar la API pública, pero hereda el cambio de comportamiento de Kitpymes.Core.Logger 2.1.0 (abajo).
Corrección de seguridad: Kitpymes.Core.Logger 2.0.0 traía dependencias con vulnerabilidades conocidas, que heredaba quien instalaba Validations.
- Alta: Microsoft.Data.SqlClient 5.0.1 (GHSA-98g6-xh36-x2p7) y Azure.Identity 1.6.0 (GHSA-5mfx-4wcx-rv27). Moderada: Azure.Identity (GHSA-wvxc-855f-jvrv, GHSA-m5vv-6r4h-3vj9), System.IdentityModel.Tokens.Jwt y Microsoft.IdentityModel.JsonWebTokens 6.21.0 (GHSA-59j7-ghrg-fj52), MailKit 2.6.0 (GHSA-9j88-vvj5-vhgr) y MimeKit 2.6.0 (GHSA-g7hc-96xr-gvvx).
- Pasa a Kitpymes.Core.Logger y Kitpymes.Core.Logger.Abstractions 2.1.0, que las corrige.
- Sin cambios en la API pública ni en el código de Validations. El log por email de Logger cambia de comportamiento en la 2.1.0 (ver sus release notes): quien instala Validations recibe Serilog 4.x y MailKit 4.x como dependencias transitivas (NU1605 si fijaba Serilog 3.x o MailKit 2.x) y los lotes que fallan se reintentan más tarde.

# v.2.0.0
Versión mayor: rompe a quien venga de la 1.0.8 (la última publicada en NuGet, .NET 5). Abajo, qué cambia y cómo migrar.

- Requiere .NET 10 o superior.
- Usa las librerías Kitpymes ya migradas desde NuGet (Shared 2.0.1, Results 1.0.1, Logger 2.0.0); quien la use debe migrar también esas (ver sus release notes).
- El código pasa a github.com/kitpymes/kitpymes-core-validations y el paquete se publica desde GitHub Actions.

## Cambios incompatibles y cómo migrar desde 1.0.8

1. Espacios de nombres: antes había tres (Kitpymes.Core.Validations, .Abstractions y .FluentValidation).
   - Kitpymes.Core.Validations.Extensions, .Settings y .Middleware: carga, configuración y middleware.
   - Kitpymes.Core.Validations.Abstractions.Exceptions: excepciones de validación.
   - Kitpymes.Core.Validations.FluentValidation.Extensions y .Settings: integración con FluentValidation.

2. Reglas de FluentValidation
   - RuleBuilderExtensions se reparte en una clase por regla (EmailRuleBuilderExtensions, FileRuleBuilderExtensions, RegexRuleBuilderExtensions, etc.). Los métodos se usan igual añadiendo el using de Kitpymes.Core.Validations.FluentValidation.Extensions.

3. Clases eliminadas
   - Messages y Resources: los mensajes vienen de Kitpymes.Core.Shared.
   - ValidationsOptions.WithFluentValidation(params string[] assemblies): la configuración de FluentValidation pasa a sus Settings.
